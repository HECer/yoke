## Goal and decision

Fix measurably avoidable setup, diagnosis, integration, and evidence failures. Yoke should reliably show what is running, why something is blocked, and which time/usage data is complete or unknown. Quality, HEAD, source, and protected acceptance gates remain mandatory.

A minor release, 1.23.0, is recommended because additive diagnostic/telemetry contracts are being introduced alongside bug fixes. Alternatives: 1.22.1 limited to immediate P0 fixes, or a larger scheduler/routing redesign. The small hotfix is insufficient for correct measurement and evidence; the redesign lacks a measured scheduler bottleneck.

Out of scope: a new dashboard UI, new models/providers, cloud telemetry, installation of other plugins, weakened tests, blanket sandbox expansion, guaranteed efficiency percentages. Do not start native subagents from a Yoke worker. Use existing recovery, evidence, context, and telemetry modules before making changes.

## Architecture and contracts

CLI exploration remains read-only. Preflight separates configuration from operational capabilities. The existing reporter remains the shared status basis for the CLI and consumers. Infrastructure failures receive structured causes. Artifacts are retained with source binding before cleanup. Integration uses the existing locks and fingerprints; a lost lock or changed HEAD can never appear as success.

Telemetry is extended locally and additively. Missing guardian/approval data is unknown; a session inaccessible through the provider is not replaced with zero cost. New fields distinguish measured values, derived values, and coverage. No second orchestration layer.

## Story set and Definition of Done

Every story starts with a reproducibly failing behavior test. No production change before RED. Extend existing tests instead of creating parallel test infrastructure. After GREEN, run focused checks and required integration/protected gates. A detailed step plan and PRD are created after approval.

### E1 — Help and flag validation without side effects

Files: `src/cli.ts`, CLI tests under `tests/`.

- `yoke setup --help`, `yoke retrofit --help`, and corresponding `-h` invocations display help and exit 0 without configuration, file, process, or registry mutation.
- Help also works with a specified target path. Tests compare complete file-tree contents and relevant dispatch spies before/after invocation.
- Unknown or incompatible flags for mutating commands are rejected before dispatch with exit != 0 and a clear cause. Existing documented invocations remain compatible.
- Shared CLI help is reused; no new CLI framework redesign.

### E2 — Runtime files and clean resumption

Files: `src/retrofit/gitignore.ts`, `src/loop/git.ts` only if a remaining gap is actually demonstrated, `tests/retrofit/gitignore.test.ts`.

- Retrofit ignores `.yoke/supervision/` idempotently and preserves existing ignore entries.
- The existing exception in `RUNTIME_PATHS` is accounted for; no broad exemption for other `.yoke` files.
- Integration test: PRD assessment/supervision alone does not dirty a freshly configured checkout; an untracked user file still blocks it.
- Already tracked runtime files are not deleted without an explicit migration or silently removed from the index; diagnostics identify them.

### E3 — Correct compact parallel status

Files: `src/loop/run-command.ts`, `src/loop/reporter.ts`, `tests/loop/loop-status-render.test.ts`, `tests/loop/parallel-status-regressions.test.ts`.

- Compact status includes active workers with story/phase, active integration, and waiting state. No `undefined`, and no `story=none` as the sole description while story workers are active.
- Serial status, no status file, an empty worker pool, integration without implementation workers, and a completed loop are tested.
- Existing top-level fields remain compatible; parallel fields are additive and sorted deterministically. Compact output remains on one line.
- Removing integrator status alone does not report integration completion. Success follows only confirmed integration; rejection has its own message.

### E4 — Browser diagnostics with the actual cause

Files: `src/smoke/command.ts`, `tests/smoke/command.test.ts`, `tests/smoke/journeys.test.ts`.

- Package resolution, a missing browser binary, clear sandbox/permission failures, and other launch failures are reported separately.
- Unclear failures remain `launch-failed` with a redacted original cause; no speculative sandbox diagnosis from arbitrary error text.
- Exit != 0 on startup failure, no successful flow evidence, and no request to install a package that is already available.
- Successful starts, target-relative package resolution, Windows paths, cleanup, and source-fingerprint behavior remain tested.

### E5 — Operational preflight for RTK and code intelligence

Files: `src/retrofit/planners/codex.ts`, `canon/tools/codex-rtk-hook.mjs`, `src/code-intelligence/mcp-server.ts`, `src/code-intelligence/coordinator.ts`; locate existing audit/setup/backend modules before extending them. Tests: `tests/retrofit/planners-codex.test.ts`, `tests/retrofit/codex-rtk-hook.test.ts`, `tests/code-intelligence/mcp-client.test.ts`, plus relevant existing backend tests.

- RTK integration is idempotent; migrate only Yoke's own legacy hooks and preserve third-party hooks. Do not claim automatic compression when the native hook is missing.
- Check the actual Codex tool schema and installed RTK version; use native responses. Do not automatically claim shell rewriting for nested code-mode invocations.
- Preflight separately shows the configured mode, resolvable workspace identifier, and actual backend coverage. Missing backends produce an explicitly degraded status and documented fallback.
- The configured workspace identifier is either the actually accepted identifier or is rejected with a clear migration diagnosis; no silently ignored setting.
- No cross-workspace queries for unknown workspace IDs. Read-only preflight does not change the project.

### E6 — Preserve candidates, evidence, and completion correctly

Files: existing candidate/integration/evidence/cleanup modules under `src/loop/`, `src/smoke/command.ts`; extend existing recovery/completion tests.

- Required evidence remains available after isolated integration/cleanup, with source/configuration/environment binding and a file-hash manifest. Retention uses existing evidence contracts.
- Evidence with path traversal or symlink escape is not collected. Failed collection prevents completion; the candidate is retained for recovery.
- Completion reruns write to a runtime path; selected final assets are explicitly collected once. User changes are never automatically included in commits.
- Integration reports busy until actual acceptance. Source/HEAD changes continue to cause rejection and invalidate old evidence.
- For an unchanged candidate, recovery first reverifies/reintegrates; implementation occurs only when a specific repair is needed. Inspect the existing recovery path for this purpose rather than bypassing it.
- Advisory locks cannot forcibly stop external processes; fingerprint/HEAD checks remain the mandatory protection.

### E7 — Actual write scopes and isolated runtime caches

Files: existing scheduler/worker/candidate/worktree/dependency modules; tests: existing parallel/recovery/scheduling tests.

- The candidate diff is checked against `writes`. Diagnose path deviations with changed files and potential sibling collisions. Declarations are not a sandbox.
- On an unexpected collision, do not integrate based on an old non-overlap assumption; use existing acceptance/recovery contracts.
- A shared package download cache is permitted; writable runtime caches belong to the worktree. No writes to root `.vite-temp` and no blanket sandbox relaxation.
- Network failures are separated from test/code failures. Offline cache misses are explicitly reported; no blind endless retries.
- Package/lockfile changes invalidate reuse; measure cold/warm setup separately.

### E8 — Complete local time/usage overview

Files: existing provider/telemetry/event/reporter modules, existing telemetry tests.

- Per role and attempt: measured input, cache reads, output, usage source, coverage, and missing data. Do not double-count provider/parent/child views.
- Collect guardian/approval data only when available from the host and unambiguously attributable. Otherwise report a coverage gap instead of 0 or an invented total.
- Report worker process duration, the sum, and the union duration of parallel intervals separately. Infrastructure/observer/product failures are separate categories.
- Missing prices remain unknown. Cache reads remain included in input. Do not add reasoning output again.
- Routine status observation requires no model call; use existing local events. Visible measurement gaps remain visible.

### E9 — Evidence of improvement and release

- Accept regressions from the NEXUS run as deterministic harness cases; reproduce the layout defect with populated incident/event state and visible panel bottom edges in the project benchmark.
- Browser evidence requires confirmed server startup and traceable app/source identity. Another server's occupied port is recognized as an error, not valid evidence.
- Paired before/after benchmark under controlled conditions; first stage at least three pairs per cold/warm state, with the measurement harness read-only during source gates.
- Results include sample count, empirical range, open wait/cost gaps, and unchanged test quality. No guaranteed saving.
- The production diff receives independent code review and independent security review where relevant boundaries are involved. The implementer does not take on these roles. Missing evidence blocks a release claim.
- Release checks: `npm run lint`, `npm run build`, `npm test`, `npm run docs:check`, `npm run package:check`, `npm run audit:ci`, plus the repository's protected/integration gates.
- Synchronize the version only for the completed release: package/lockfile, Canon/provider manifests, README; a dated CHANGELOG with behavior, migrations, and limitations. Tag/publish only after release gates; confirm GitHub CI/npm publication before treating the release as published.

## Order and limitations

1. E1–E4: immediate reproducible failures.
2. E5: no claimed efficiency tools without operational functionality.
3. E6–E7: evidence, integration, and parallel write/cache boundaries.
4. E8: a complete and honest measurement basis.
5. E9: comparison and release.

For E6–E8, narrow down the current call graph and existing contracts before implementation. The measurement proves the failure in the benchmark, but not that every current path has the same remaining gap. Existing correct protections are preserved.

Do not derive a time forecast for these stories from the seven UI stories. Do not trigger installation or authenticated model benchmark costs solely on the basis of this draft. After approval, create a detailed execution plan and validated PRD; then begin implementation test-first.
